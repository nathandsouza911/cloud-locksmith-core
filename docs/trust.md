# Trust: what Cloud Locksmith Core can do in your tenant

Read this before you connect a real tenant. Every statement here points at the code or a
test; if they disagree, the code wins and this page has a bug.

**Short version.** You run it yourself. With a full connect it holds delegated Microsoft
Graph tokens that include **write** scopes, so it *can* change users, Conditional Access,
the authorization policy and admin role assignments. It changes nothing until a person
approves a specific fix (automatic fixes are off by default). A Preview sign-in requests
no write scope and its token is not stored. Tenant data stays in your Postgres database
until you delete it.

Also possible: an **app-only** token (client credentials) for the tenant set in
`MICROSOFT_TENANT`, used to disable accounts during offboarding. It needs the application
permissions in `REQUIRED_GRAPH_REMEDIATION_PERMISSIONS` (default
`User.EnableDisableAccount.All`), which you grant yourself in Entra. Leave
`MICROSOFT_TENANT` unset and grant nothing if you do not want this.

The demo (`DEMO_MODE=true`) requests no scopes and makes no outbound requests at all
(`backend/tests/test_demo_mode.py`).

## 2. Preview sign-in: what it stores and what it does not

* Gives `READ_ONLY` access; every change route refuses it (`require_write_access`).
* The access token is used for one scan during sign-in and is **not stored**
  (`_stage_tenant_token` skips the `preview` intent in
  `backend/app/api/routes/auth_microsoft.py`).
* The **scan results are stored**: the tenant record, your user record, and the findings,
  snapshots and directory data listed in section 5. They stay until you delete them.

## 3. Tokens and secrets

* Delegated access and refresh tokens are stored in `tenant_oauth`, both encrypted with
  Fernet using `ENCRYPTION_KEY` (`backend/app/services/crypto.py`,
  `backend/app/services/token_manager.py`). A copy of the database without the key does
  not reveal them.
* The dashboard session is an app JWT (`APP_JWT_SECRET`) in an HttpOnly, Secure cookie.
  Logout puts it on a Redis deny list.
* Every Graph call checks that the token's tenant (`tid`) is the tenant being acted on.
* Nothing is sent anywhere except: Microsoft (`login.microsoftonline.com`,
  `graph.microsoft.com`); Resend (`api.resend.com`), only if you set `RESEND_API_KEY`
  (verification, alert and support emails); and webhook or Slack URLs that a tenant
  owner or admin adds as notification targets. There is no telemetry or analytics. The
  code contains a Google Workspace connector, but no sign-in path creates a Google tenant.

## 4. What it can change, and what stands in front of a change

What can change, with a full connect:

* **Fixes** for the controls marked *Fix* in `controls.md`: Conditional Access policies
  (created report-only by default), the authorization policy (guest invites, user
  consent), users (for example disabling an unused account), admin role assignments.
* **Offboarding** of a user you select: revoke sessions, remove admin roles, disable the
  account.
* **Rollback** of a fix, from the snapshot taken before it.

Gates (details and tests: `remediation-lifecycle.md`, `threat-model.md`):

* A person approves each fix; approval expires after 48 hours. Automatic fixes need
  `ENABLE_AUTO_REMEDIATION=true` (default `false`) and apply only to the *Auto-fix list*
  in `controls.md`.
* Only OWNER or ADMIN of the tenant can approve or execute, and only after a Microsoft
  sign-in in the last 24 hours. Preview access cannot.
* Pre-flight checks run before execution and refuse on failure. Every Conditional Access
  change needs a registered break-glass account that Microsoft confirms is an active
  Global Administrator, and excludes it from the policy.
* One fix at a time per tenant (lock); attempts are limited; the result is read back
  from Graph to verify it.
* Every step is written to the remediation audit log; break-glass registrations and
  offboarding are written to the hash-chained audit log, and refused if that record
  cannot be saved.

## 5. What tenant data it keeps, and for how long

Stored in your Postgres database, per tenant:

* Directory data used by the controls: users (display name, email, admin and break-glass
  flags, last sign-in), Conditional Access policies, MFA registration state, and the raw
  scan snapshots they are computed from.
* Findings with their evidence (which can include UPNs and policy settings), posture
  scores and snapshots over time.
* Fix records: approvals, the before snapshot and after state of each change, verification
  results, rollbacks, and the audit logs.
* Reports you generate (PDF), alerts, break-glass sign-in events (time, IP, location),
  support tickets, notification targets.
* The encrypted tokens (section 3).

**Retention:** the code deletes none of this automatically. It stays until you delete the
tenant or the database.

## 6. How to delete it

* **One tenant:** Settings → **Delete Account** (OWNER or ADMIN; type `DELETE`). Tokens are
  wiped first, then every row of the tenant in every table. Only a deletion record is kept
  (tenant ID, tenant name, which user deleted it). A test fails if a new table with a
  tenant ID is not covered (`backend/tests/integration/test_tenant_deletion_complete.py`).
  Releases up to 0.1.1 missed some tables; see `CHANGELOG.md`.
* **Everything on a local install:** `docker compose down -v` in `backend/` removes the
  database volume.

## 7. How to revoke its access in Microsoft

Deleting data in Cloud Locksmith does not remove its permission in your tenant. To do that:

1. In the Entra admin center, open **Enterprise applications** and select your Cloud
   Locksmith app registration's enterprise app.
2. Either **Permissions** → review and revoke the granted permissions, or **Properties** →
   **Delete** to remove the app from the tenant entirely.
3. If you granted application permissions for offboarding, remove them too (they are part
   of the same enterprise app).

After this, the stored refresh token no longer works. An access token that was already
issued stays valid until it expires (usually about an hour). If you suspect misuse, also
revoke the sessions of the account that connected the tenant.
